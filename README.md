# Just Fun · 模块化工程源码

本工程沿用 v6.21 开始的模块化架构，以 v6.48 的元数据保险箱和 v6.49 的书房一期为已验证开发基础，当前为 **v6.64「PDF 手势性能与锐化精修」**，保持单文件最终交付。

## 本地构建（模块化工程已包含 PDF.js 6.4.299 离线资源，无需 npm install）

前提：Node.js 22+。运行：

```sh
node scripts/build.js
```

自动生成 `dist/douyin.js` 和 `dist/build-report.json`。构建只使用 Node 内置模块；不访问网络、不下载依赖。用户只需要 **dist/douyin.js**；运行时对 FFmpeg、FFprobe 的原有要求不变。

## 以后如何修改

- `src/client/index.html`：页面骨架，包含 `JUSTFUN_CSS`、`JUSTFUN_JS` 两个构建占位符；不要删除。
- `src/client/styles/`：分层 CSS，按 `build.manifest.json` 既定顺序串接。新 UI 优先整理旧规则，避免无休止尾部覆盖。
- `src/client/scripts/`：浏览器 JavaScript，按职责拆为状态、音频、图片、媒体卡片、播放器、视频工具、多开、事件等；按清单顺序执行。
- `src/server/`：启动、安全、索引、媒体管理、HTTP、进度、路由、监听与生命周期。
- `src/media/`：截图/逐帧、音频与 FFmpeg 转码。
- `assets/favicon.ico`：构建时嵌入 `douyin.js`，**发布时不需要外部资源文件**。
- `build.manifest.json`：决定源码拼接顺序。没有依赖图必要性时不修改顺序。
- `scripts/build.js`：本地离线构建器，不对源文件进行格式化或重排。

**重要：这个版本是“安全拆分与模块化维护基线”，而不是把每个文件改写成 CommonJS/ESM。** 旧代码中仍存在跨文件顶层变量、函数及事件处理的共享上下文；构建器故意在同一作用域中拼接，避免一次性重写破坏行为。以后可以在有测试保障的前提下逐步减少隐式依赖，切勿一次大爆炸改造。

**今后只修改 `src/` 和 `assets/`；`dist/douyin.js` 是生成产物，不作为长期编辑对象。**

## v6.23：真实工作/学习目录与视频兼容转码

- 控制台选择目录时显示已输入的内容，可以粘贴路径；密码输入仍保持隐藏。
- 新的虚拟 `source/` 导航树只读地索引原有子文件夹，保留 Unicode 目录名及层级；只采集视频、音频、图片，排除文档、压缩包、符号链接、缓存目录、保留的 `data/` 目录。只显示具有媒体后代的子目录。
- 混合资料根目录中的媒体也只读保护，不会因开启 Hash 而自动改名。受管理 `data/` 与纯媒体库仍保留 v6.21 操作语义。
- 每个视频右键/“⋯”菜单均可选择「兼容性检测 / 转码」；FFprobe 给出保守的无损重封装或高质量 H.264/AAC 建议，也可对看似兼容但播放卡顿的视频手动强制重编码。
- 转码会把新的 MP4 副本放到受管理 `data/`，不覆盖源文件；使用 FFmpeg 实际处理进度显示。自动复制模式保持音视频比特流不变，重编码使用 libx264 CRF 18、yuv420p、AAC 256k。
- 输出保留常规 metadata / chapters，但不包含内嵌字幕和附加数据轨；有字幕需求需保留原片或单独处理，不能宣称完整无损。
- 安全措施：混合工作资料不允许启用会执行「三次输错密码清空目录」的 Hash+密码危险组合；专用媒体库保持原有规则。建议在工作目录使用普通模式或首次初始化时仅加 `--pwd`。
- 媒体索引只在文件发生变化后重试先前失败的 FFprobe/封面任务；大目录处理会定期让出事件循环。但扫描性能仍需在真实 Windows 和大规模文件库单独验收。

专项回归：`python tests/workspace.py`（独立临时目录、真实 FFmpeg 转码与浏览器注入测试），绝不输入用户真实资料路径。

## v6.26：截图/封面卡死与重启恢复

- `writeCover()` 不再同步阻塞 Node HTTP 事件循环；封面请求和启动自动补封面都使用异步 FFmpeg。
- `probeVideo()` 从同步 `spawnSync` 改为异步并限时（15 秒），长资料库/坏视频探测期间仍能访问其他页面。
- `captureFrame()` 60 秒超时；非帧序号截图采用输入侧精确 seek，不再从零解码整个长视频。原件从不被覆盖。
- 后台预览超过 2400 帧时不批量生成 JPEG（视频仍可 seek、截图/封面），其他视频生成也限定 60 秒。
- 旧帧缓存淘汰改为异步清理，不阻塞启动；进程退出会终止当前启动的 FFmpeg/FFprobe。
- 启动阶段向终端报告进度，不再只显示目录提示；出错时输出可定位的错误原因。
- 新增 `tests/recovery-v626.py`，模拟阻塞 FFmpeg、关闭期间仍在处理的截图、重新启动同一个隔离目录以及长视频批量缓存保护。

**注意**：没法从 Linux 环境证明用户 Windows 实机上的这次故障已完全解决，必须观察用户终端日志确认。现场真实媒体/缓存未被访问、删除、改名或修改。

## v6.28：完整长视频逐帧时间轴

- 取消逐帧估算中 120000 帧的硬截断。2 小时 56 分钟、30fps 的视频显示约 316800 帧，实际值依源文件帧率而定。
- 大于 30 分钟的视频优先由 FFprobe 元信息获取帧率和时长，避免扫描全部 packet。超过 2400 帧的估算结果采用虚拟时间轴，只返回 count、fps、duration，不返回大数组。
- 短视频保留精确时间戳模式；长视频根据估算位置使用时间戳精确 seek 提取截图和封面，原素材不覆盖。VFR、异常帧率的估算结果只供快速定位，非严格原帧序号。
- 预览后台任务独立读取 total frame count，仍阻止长视频生成海量 JPEG。
- 新增 `tests/long-video-frames-v628.py`（Chromium、真实 FFprobe 服务端、隔离模拟元数据），纳入 `tests/run-all.py`。
